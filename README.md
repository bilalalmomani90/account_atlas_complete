# Account Atlas — المراحل 1 إلى 6 (كُتبت كاملة، لم تُترجَم بعد)

**حالة التحقق:** الكود كُتب دون إمكانية تشغيل Flutter/Dart في بيئة الكتابة. لم يُبنَ ولم تُشغَّل أي من اختباراته (نحو 35). أول تشغيل لـ GitHub Actions هو أول اختبار حقيقي؛ أرسل لي أخطاءه لأصلحها.

## الرفع إلى GitHub
1. فك ضغط الملف، وأنشئ مستودعاً **خاصاً** جديداً على GitHub.
2. ارفع **محتويات** المجلد `account_atlas` (وليس المجلد نفسه) بالبنية نفسها، ويجب أن يظهر `.github/workflows/ci.yml` و`release.yml` في جذر المستودع.
   - الأسهل من حاسوب: Add file > Upload files واسحب كل المحتويات (تحفظ المتصفحات المجلدات عند السحب)، أو `git push`.
   - من الهاتف فقط: رفع المجلدات عبر المتصفح غير مدعوم عادة؛ استخدم تطبيق Termux مع `git`، أو أنشئ الملفات من github.dev.
3. تبويب Actions > ci > Run workflow. حمّل الـ APK التجريبي وبناء Windows من Artifacts.
4. بعد نجاح ci: أنشئ مفتاح التوقيع وأضف الأسرار (انظر «المرحلة 6») ثم شغّل release.

## نقاط التحقق المعروفة
- صيغة `hooks: user_defines: sqlite3: source: sqlite3mc` في `packages/atlas_core/pubspec.yaml` من وصف وثائق Drift ولم أتحقق من الصياغة الدقيقة.
- أرقام إصدارات الحزم تقريبية (drift، uuid، flutter_secure_storage، path_provider).
- مجلدا android/windows يُولَّدان في CI بـ `flutter create`؛ ضبط الحد الأدنى/الهدف API 36 يضاف قبل أول إصدار.
- المرحلة 1 مكتملة كتابةً (شاشات + لوحة تحكم + اختبار استمرار). لقطات RTL واختبار ترحيل حقيقي مؤجلان؛ التجربة الفعلية مؤجلة للمرحلة 5 بطلبك.

## المرحلة 2 (كُتبت، لم تُبنَ ولم تُختبر)
- الهويات، جداول الربط (idempotent، إعادة الربط تستعيد الرابط نفسه)، صفحات التفاصيل للحساب/البريد/الهوية/المشروع/المورد/الموقع، الملاحظات.
- سجل التغييرات + التراجع (إضافة/تعديل/حذف). الحذف دائماً منطقي.
- البحث الشامل: **في الذاكرة مع تطبيع عربي** (تشكيل، أ/إ/آ→ا، ى→ي، ة→ه) بدل FTS5 كما اقترحت في التقرير: أبسط وأضمن دون اختبار. يُراجَع إلى FTS5 إن ظهر بطء عند آلاف السجلات.
- خريطة العلاقات: عرض متدرج (مركز + عمق 1-3) مع تصفية بالنوع وتكبير/تحريك ونقر لفتح التفاصيل.
- المتبقي: كشف التكرار (المرحلة 3 كما اقترحت)، التحرير المباشر لحقول الكيانات من الواجهة (الدالة updateFields جاهزة)، الحقول المخصصة والمرفقات (جداولها موجودة بلا واجهة).

## المرحلة 3 (كُتبت، لم تُبنَ ولم تُختبر)
- تصدير JSON كامل (بالمعرّفات والعلاقات وشواهد الحذف، بلا أي أسرار) وCSV لكل كيان.
- استيراد JSON/CSV عبر: معاينة ← مطابقة حقول (اقتراح تلقائي عربي/إنجليزي) ← كشف تكرار ← قرار لكل عنصر ← تأكيد ← تنفيذ في معاملة واحدة (كل شيء أو لا شيء) مع فحص المفاتيح الخارجية، والتراجع عن الاستيراد كله بنقرة.
- الافتراضي دائماً الأكثر أماناً: المتغيّر يبقى نسختك، المكرر يُتجاهل، لا حذف أبداً.
- كشف التكرار على البيانات الحالية + دمج بموافقة (يعيد توجيه كل العلاقات والملاحظات ويمكن التراجع). اشتراك بريد لا يجعل حسابين مكررين.
- **انحراف عن التقرير:** منطقة التجميع (import_sessions) في الذاكرة بدل جدول، لأن الخطة تُبنى وتُطبَّق في الجلسة نفسها.
- نقاط للتحقق: واجهة file_picker (saveFile/pickFiles) وسلوكها على Android وWindows؛ RadioGroup يحتاج Flutter حديثاً (3.35+).
- النسخ الاحتياطي المشفر والتحقق قبل الاستعادة: المرحلة 5.

## المرحلة 4 — التكاملات الرسمية (قراءة فقط)
- `atlas_core/lib/src/integrations.dart`: نقل HTTP قابل للحقن، GitHub (Device Flow + اكتشاف المستودعات والإيميلات)، Supabase (`GET /v1/projects`)، Firebase (`GET /v1beta1/projects` مع ترقيم الصفحات)، وخدمة `IntegrationService`.
- القواعد: لا حذف أبداً؛ ما اختفى من المصدر يُعلَّم `needs_review` (`missing_from_source`) ويُزال العلم إن عاد؛ الحساب اليدوي المطابق (نفس الموقع واسم المستخدم) يُتبنّى لا يُكرَّر؛ عنصر حذفه المستخدم لا يُبعث؛ المعدَّل يدوياً لا يُكتب فوقه؛ كل مزامنة دفعة واحدة قابلة للتراجع من سجل النشاط.
- المفاتيح: في مخزن النظام الآمن فقط (`secret_ref` مؤشر)، ولا تظهر في `sync_history` أو الأخطاء.
- واجهة: صفحة «التكاملات» (ربط/مزامنة/فصل، قائمة المراجعة، سجل المزامنة).
- متحقق منه رسمياً: حد GitHub 5000 طلب/ساعة للمستخدم ورؤوس `x-ratelimit-*` (403/429)، نقاط Device Flow وأكواد الأخطاء، حقول Supabase `/v1/projects` وصلاحية `projects_read`.
- غير متحقق: رأس `Authorization: Bearer` لـ Supabase (معيار شائع لم تذكره الصفحة)، تفاصيل `GET /user/repos` (المعاملات من نمط نقاط مشابهة)، صلاحيات Firebase داخل Device Flow لدى Google (غالباً غير مدعومة، لذا Firebase بلصق رمز مؤقت الآن؛ تسجيل دخول Google الكامل يحتاج Client ID ويُقرَّر في المرحلة 5/6)، حد Firebase.
- لم يُجرَّب شيء: الاختبارات `test/phase4_test.dart` (7 اختبارات بخادم وهمي) جاهزة للتشغيل في CI.

## المرحلة 5 — النسخ المشفّر، المزامنة الاختيارية، قفل التطبيق
- **نسخ احتياطي مشفّر** (`secure_backup.dart`): PBKDF2-HMAC-SHA256 (600k تكرار) + AES-256-GCM، الترويسة مربوطة كـ AAD لكشف العبث. بعد الحفظ يُفك التشفير فوراً ويُقارن بعدد صفوف كل جدول؛ فشل المقارنة = «لا تعتمد على هذه النسخة». الاستعادة = استيراد عادي بمعاينة وقرارات (الأكثر أماناً افتراضياً) وقابل للتراجع. الامتداد `.atlasbak`.
- **مزامنة عبر مجلد مشترك** (`sync_folder.dart`): كل جهاز يكتب لقطته المشفّرة `<deviceId>.atlas-sync` فقط ويدمج لقطات الأجهزة الأخرى. لا خادم ولا حساب. الدمج صفاً بصف: الأحدث يفوز، وعند التساوي يُحسم بمقارنة محتوى ثابتة فيتقارب الجهازان. الحذف نعومة (tombstone) ينتقل كصف عادي. التعارض الحقيقي (تعديل على الجهازين بعد آخر مزامنة ناجحة) يُسجَّل في السجل مع النسخة الخاسرة وتظهر في شاشة «المزامنة» بزر «إبقاء الحالي / استخدام الأخرى». أي مخالفة لمفاتيح العلاقات تُلغي الدمج كله (rollback).
- **قفل التطبيق**: رمز PIN (PBKDF2 مع ملح) في مخزن النظام الآمن، يُطلب عند الفتح وبعد 30 ثانية في الخلفية، مع تأخير متصاعد بعد 3 أخطاء. يحمي الواجهة فقط؛ القاعدة مشفّرة بمفتاح عشوائي منفصل.
- **قرارات وانحرافات**: البصمة/Windows Hello مؤجلة للمرحلة 6 (local_auth يتطلب FlutterFragmentActivity وإذناً ولم يُتحقق من دعم Windows). سجل النشاط والتكاملات لا تُزامَن (حجم/أسرار). الاعتماد على ساعات الأجهزة (LWW)؛ انحراف كبير بين الساعات قد يعطي فائزاً خاطئاً — لذلك تُحفظ النسخة الخاسرة دائماً.
- **غير متحقق**: إصدار حزمة `cryptography`؛ أن 600k هو الرقم الحالي الموصى به؛ وصول `dart:io` إلى مجلد اختاره المستخدم عبر `file_picker` على Android (قيود التخزين المحدد Scoped Storage) — قد يعمل على Windows ويحتاج اختباراً على Android؛ مزامنة مجلد سحابي تتأخر عن الفوري.
- **الاختبارات**: `test/phase5_test.dart` (تشفير/عبث/كلمة خاطئة، تحقق واستعادة، PIN، مزامنة جهازين: نشر، حذف، تعارض، حل التعارض، ملف خاطئ). لا Dart في بيئتي ولا شبكة، فالتشغيل الفعلي الأول سيكون على GitHub Actions.

## المرحلة 6 — التدقيق الذكي، التعديل، الإصدار
- **التدقيق** (`audit.dart` + صفحة «التدقيق»): قراءة فقط. يقترح: عناصر اختفت من المصدر، تجديدات قريبة/متأخرة (خلال 30 يوماً)، حسابات بلا بريد، حسابات لم تُراجَع منذ سنة (زر «تمت المراجعة» يعيد العدّاد وقابل للتراجع)، حسابات بلا هوية (إن وُجدت هويات)، بريد غير مرتبط، مواقع/مشاريع فارغة، موارد يتيمة. لا يغيّر شيئاً بنفسه. (الحقل `renewal_date` لا يوجد له إدخال في الواجهة بعد.)
- **التعديل**: زر ✎ في كل صفحة تفصيل لحقول النص (مسجّل في السجل وقابل للتراجع؛ تعديل عنوان البريد يحدّث صيغته المطبّعة).
- **الإصدار** (`.github/workflows/release.yml`، تشغيل يدوي): يشغّل اختبارات النواة أولاً، ثم يبني APK وAAB موقّعين وزيب Windows.
  - الأسرار المطلوبة: `ANDROID_KEYSTORE_BASE64`، `ANDROID_KEYSTORE_PASSWORD`، `ANDROID_KEY_ALIAS`، `ANDROID_KEY_PASSWORD`. أنشئ المفتاح مرة واحدة بـ `keytool -genkeypair -v -keystore upload-keystore.jks -keyalg RSA -keysize 2048 -validity 10000 -alias upload` ثم `base64 -w0 upload-keystore.jks`. احفظ نسخة منه خارج GitHub؛ فقدانه أو تغييره يمنع تحديث التطبيق.
  - `versionCode = VERSION_CODE_BASE (متغير اختياري) + رقم التشغيل`، فلا ينقص أبداً. إن نشرت يدوياً من قبل برقم أعلى فاضبط `VERSION_CODE_BASE`.
  - يطبع بصمة المفتاح في السجل: قارنها بين الإصدارات.
  - `tools/configure_signing.py` اختُبر على قالب Kotlin DSL مصغّر فقط؛ سيفشل بصوت عالٍ إن اختلف القالب الحقيقي.
- **الإعلانات (Start.io)**: لم تُضف. لا حاجة حالياً؛ القرار مؤجّل لنسخة Android منفصلة (flavor) إن طلبتَها، وWindows بلا إعلانات.
- **مؤجل/معلّق**: البصمة وWindows Hello، تسجيل دخول Google لـ Firebase، حقول مخصصة ومرفقات في الواجهة، اختبار ترحيل حقيقي، لقطات RTL، FTS5 إن بطؤ البحث، خدمات إضافية (Vercel/Cloudflare/Netlify/npm).
